## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Owner request 2026-10-31, redefined with the owner 2026-11-02/03 (advisor review: /tmp/levana-task55-proposal.md). Present Levana the same way on Play, F-Droid and GitHub, keep the screenshots reproducible, and update the store listing as part of each release, **only with owner approval**.

**Owner decisions (2026-11-02/03)**
- **No feature catalog, no hash/approval manifest, no pixel-based staleness checks.** A hand-maintained document, `specs/STORE_LISTING.md`, records what the screenshots, the store text and the walkthrough show. Which shots need updating is decided from the tasks and commits.
- **One store text for Play and F-Droid**: `fastlane/metadata/android/en-US/` (title, short and full description). Play's listing is uploaded from it; F-Droid reads it from the tag.
- **Screenshots**: 8 phone shots, **1080×1920 (9:16)**, RGB PNG without alpha, generated by a Roborazzi test (`StoreScreenshotTest`) and written straight into `fastlane/metadata/android/en-US/images/phoneScreenshots/`. It is opt-in and not part of the normal verify run; it can render selected shots only. No widget or Quick Settings shots. Order:
  1. Month view in Hebrew months (light; owner 2026-11-03: no dark-mode shot)
  2. Month view in Gregorian months
  3. Hebrew interface
  4. Agenda (with a yahrzeit and an anniversary)
  5. Day sheet expanded on erev Shabbat
  6. Zmanim, full list
  7. Event editor with the Hebrew/Gregorian date picker
  8. Sidebar open, showing the saved cities
- **Nothing under `fastlane/` is committed without the owner's explicit approval** (text, screenshots, icon, feature graphic, changelogs).
- **Change detection**: a task that visibly changes a screen in a store shot, or something the store text or walkthrough describes, gets the label `store-listing` and a one-line "Store listing:" note. At release, the coordinator checks the labelled tasks merged since the last tag (merge commits name their task) and skims the commits against STORE_LISTING.md.
- **Release flow** (owner says "release vX.Y.Z"):
  1. The coordinator regenerates only the affected shots and drafts the changelog and any text change.
  2. The owner approves.
  3. The coordinator commits, then tags.
  4. CI uses `changelogs/<versionCode>.txt` as the GitHub release notes and Play "What's new" (`whatsNewDirectory`). It uploads the listing (text and images; no AAB, no changelogs) with fastlane `supply` **only when `fastlane/` changed since the last upload**, tracked by the tag `store-listing-published`. There is no GitHub environment approval gate, because approval happens before the commit.
- **Changelog check**: not a hard failure. release.yml warns when the file is missing or over 500 characters and continues.
- **Play credentials**: the upload uses the existing `PLAY_SERVICE_ACCOUNT_JSON` for now (TASK-58 tracks the rotation and the listing permission).
- **Timing**: make the first set on today's UI now and regenerate after TASK-57 redesigns (57.2, 57.5, 57.21, 57.22) through the same flow. TASK-53.5's technical work starts now; only the submission (53.6) waits for this task's approved assets.

**Still open (owner)**:
- the store text wording: the offline claim in the description, feature graphic, privacy policy and README; whether to add feature bullets; TASK-57.1 terminology;
- English only for now.

The TASK-53.4 Fastlane files remain the draft input.
